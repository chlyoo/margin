# Margin 디자인 원칙

> **요약**: Margin의 화면은 **내용을 중심에 두고 도구는 부를 때만 꺼내 쓰도록** 설계합니다. 새 기능을 넣거나 화면을 고칠 때는 이 문서의 7가지 원칙과 마지막 점검표를 기준으로 결정하십시오.

## 전체 화면 구조

파일 내용과 변경 내역이 화면 중앙을 차지하고, 나머지 도구는 가장자리에서 단축키로만 열고 닫습니다.

```
+-----------------------------------------------+
| [중앙 상단]                                   |
| 탭: [파일 | 변경 따라가기 · 확인 전 N]        |
| 파일 제목 / 코드 정리 (⌥⌘L)                   |
+-----------------------------------------------+
  |
  +--> [중앙 본문]
  |    마크다운(원문/미리보기) 또는 코드 보기
  |    열린 파일이 없으면 안내 문구와 단축키 표시
  |
  +--> [왼쪽] 파일 트리 사이드바 (⌘K ⌘B)
  |    파일 목록 탐색, 필요할 때 숨김
  |
  +--> [중앙 하단] 터미널 패널 (⌃`)
  |    기본 숨김, 단축키로 호출
  |
  +--> [오른쪽] Claude 패널 (⌥⌘B)
  |    기본 닫힘
  |    대화 기록 / 입력창 / 중지 / 새 세션
  |    "Claude의 셸 명령 허용" 설정
  |
  +--> [하단 상태 막대]
       상태 문구 / 토글 버튼: "터미널 ⌃`", "Claude ⌥⌘B"
```

- **중앙 영역**: 마크다운과 코드, 에이전트의 변경 내역을 읽고 고치는 핵심 자리입니다.
- **주변 패널**: 파일 트리, 터미널, Claude 패널은 작업 중에 필요할 때만 단축키로 불러냅니다.
- **하단 상태 막대**: 현재 상태 문구를 보여 주고, 닫혀 있는 패널을 마우스로도 열 수 있게 돕습니다.

## 1. 내용이 중심이고 도구는 부를 때만 나타납니다

화면의 기본 상태는 읽고 쓰는 내용에 집중되어야 합니다. 보조 도구는 사용자가 명시적으로 호출할 때만 나타나야 하며, 처음 실행할 때부터 자리를 차지하지 않습니다.

- **근거 요청**
  - 2026-11-25: "claude에게 지시도 항상 띄우는게 아니라 옆에 사이드로 띄울 수 있도록"
  - 2026-11-25: "터미널은 차라리 vscode처럼 단축키 눌러서 띄울수 있게"
  - 2026-11-25: Sublime처럼 사이드바를 단축키(`⌘K ⌘B`)로 숨기고 보이게 해 달라는 요청
- **지금 구현**
  - 터미널 패널은 기본으로 숨겨져 있으며 `` ⌃` `` 단축키로 엽니다.
  - Claude 패널은 닫힌 상태로 시작하며 `⌥⌘B` 단축키로 엽니다.
  - 왼쪽 파일 트리 사이드바는 `⌘K ⌘B` 단축키로 숨기거나 보입니다.
  - 각 패널은 사용자가 마지막으로 열어 둔 상태를 기억합니다.
- **판단 기준**
  - 새로운 패널을 추가할 때는 반드시 단축키로 숨길 수 있어야 합니다. 앱을 처음 켰을 때 스스로 열려 있어서는 안 됩니다.

## 2. 손에 익은 단축키를 빌려 오며 새 단축키를 만들지 않습니다

사용자가 기존 편집기에서 쓰던 근육 기억을 그대로 쓸 수 있어야 합니다. 독자적인 단축키를 발명하는 대신 널리 쓰이는 도구의 단축키와 실행 방식을 그대로 가져옵니다.

- **근거 요청**
  - 2026-11-25: "cmd+f 누르면 ... sublime이랑 똑같은 기능", "cmd k, b"
  - 2026-11-19: "subl, code(vscode) 처럼 명령어로 실행 ... 뒤에 디렉토리 입력하면 해당 폴더에서 열리도록"
  - 2026-11-20: "sublime, pycharm에서 내가 주로 쓰던기능(python 등 언어별 formatting, 터미널 실행가능)"
- **지금 구현**
  - 파일 내 찾기는 `⌘F` (Sublime 방식), 전체 파일 찾기는 정규식·대소문자·파일 마스크를 지원하는 `⇧⌘F`를 씁니다.
  - 사이드바 토글은 `⌘K ⌘B` (Sublime 방식)를 씁니다.
  - 터미널 토글은 `` ⌃` `` (VS Code 방식), 오른쪽 보조 사이드바 토글은 `⌥⌘B` (VS Code 방식)를 씁니다.
  - 터미널에서 `margin <dir>` 명령어로 폴더를 여는 CLI는 `subl` 및 `code` 방식을 따릅니다.
  - 코드 정리는 `⌥⌘L` (PyCharm의 Reformat Code 단축키)을 씁니다.
  - 변경 사항 수락은 `Tab` (Cursor 방식)을 씁니다.
  - 사이드바에서 폴더를 더블클릭하면 펼치고 다시 더블클릭하면 접습니다 (Finder 목록 보기, Xcode, VS Code 방식).
- **판단 기준**
  - 같은 동작에 대해 Sublime, VS Code, PyCharm, Cursor가 이미 쓰는 단축키를 고릅니다. 화면의 버튼 라벨 옆에는 해당 단축키를 함께 적습니다.
  - 마우스 조작도 같습니다. 더블클릭과 펼침 삼각형처럼 macOS와 위 편집기들이 기본으로 주는 동작은 요청이 없어도 처음부터 갖춥니다.

## 3. 읽는 자리에서 바로 고칩니다

문서를 읽는 화면과 고치는 화면을 나누지 않습니다. 눈에 보이는 결과물 위에서 바로 텍스트를 수정하면 원본 파일에 그대로 반영되어야 합니다.

- **근거 요청**
  - 2026-11-18: "미리보기에 있을 때도 수정 가능하게 해 xcode의 readme view가 가장 따라할만한듯"
  - 2026-11-18: "미리보기에서 고치면 마크다운이 고쳐져야하는거임"
  - 2026-11-18: "글자크기 ... italic, bold 등 markdown에서 지원하는정도만", "하이퍼링크도 자연스럽게"
- **지금 구현**
  - 마크다운 미리보기 화면에서 바로 글을 고칠 수 있습니다.
  - 미리보기에서 고친 내용은 자동으로 마크다운 원문으로 변환되어 자동 저장됩니다.
  - 서식 도구는 마크다운 문법이 지원하는 범위(본문/제목 1~3 단계, 굵게, 기울임꼴, 취소선, 문장 내 코드, 목록, 인용문, 코드 블록, 링크, 구분선)로만 제한합니다. 글자 크기는 제목 단계로만 바뀌며, 자유로운 글자 크기나 색상은 없습니다.
- **판단 기준**
  - 사용자가 보고 있는 대상에 대해 별도의 '편집 모드' 전환 스위치를 만들지 않습니다. 서식 옵션은 파일 형식이 저장할 수 있는 범위를 절대 넘지 않습니다.

## 4. 에이전트의 변경은 순서와 이유로 읽습니다

에이전트가 고친 코드는 최종 결과만 뭉뚱그려 보여 주지 않습니다. 어떤 순서와 이유로 작업했는지 단계별로 짚어 보며 수락하거나 거절할 수 있어야 합니다.

- **근거 요청**
  - 2026-11-18: "한번에 diff만 보여주는게 아니라 어떤 순서로 어떻게 작업을 했는지 ... 왜 이걸 이렇게 수정했는지 ... git diff보듯이 또는 cursor에서 tab같은걸로 accept"
  - 2026-11-18: "제일 핵심이 markdown, code view, backtracking"
- **지금 구현**
  - 중앙 상단의 `변경 따라가기` 탭에서 작업 단계 목록을 수정 이유, diff와 함께 순서대로 보여 줍니다.
  - 각 단계는 `Tab`으로 수락하고, `Delete`로 전체 거절하며, `⇧⌫`로 '이 부분만 거절'할 수 있습니다.
  - `파일 따라가기` 기능을 제공하며, 탭 제목에 `확인 전 N` 형태로 남은 검토 개수를 표시합니다.
- **판단 기준**
  - 에이전트가 변경한 모든 내용은 작업 완료로 처리되기 전에 반드시 그 이유와 함께 단계별로 검토할 수 있어야 합니다.

## 5. 기능 하나에 자리 하나만 둡니다

같은 역할을 하는 입력창이나 탭을 여러 곳에 중복해서 두지 않습니다. 역할이 겹치면 사용자는 어디에 명령을 내려야 할지 혼란을 겪습니다.

- **근거 요청**
  - 2026-11-25: "claude 에게 지시랑 셸명령, 기록, 터미널이 뭔가 중복되어 보이는 느낌"
- **지금 구현**
  - 입력창에 있던 셸 명령 모드를 없애고 터미널 패널이 그 역할을 전담하게 했습니다.
  - 중복되던 `기록` 및 `터미널` 탭을 제거했습니다.
  - 오른쪽 입력창은 오직 Claude와 대화하는 데만 쓰며, 실행 상태는 하단 상태 막대에만 표시합니다.
- **판단 기준**
  - 새로운 버튼이나 입력창을 추가하기 전에, 이미 화면의 다른 자리가 그 역할을 하고 있는지 먼저 확인합니다.

## 6. 글은 대화처럼 읽혀야 합니다

사람이 읽는 설명과 기계가 남기는 실행 기록은 시각적으로 구분되어야 합니다. 대화 본문은 문서처럼 읽기 편하게 그리고, 기계적인 출력은 뒤로 물립니다.

- **근거 요청**
  - 2026-11-25: "claude랑 하는 대화 text가 가독성이 떨어짐"
- **지금 구현**
  - 대화창에 `나`와 `Claude` 머리말을 붙여 화자를 구분합니다.
  - 본문은 13pt 크기로 그리며 제목, 목록, 코드, 굵게, 기울임, 링크 등 마크다운 서식을 렌더링합니다.
  - 도구 호출(tool calls) 기록은 작은 회색 글씨로 들여써서 본문과 구분합니다.
- **판단 기준**
  - 사람이 읽어야 할 글을 고정폭(monospace) 생짜 텍스트로 쏟아내지 않습니다. 기계의 출력물은 시각적으로 부차적인 위치에 머물러야 합니다.

## 7. 상태는 화면이 알려 줍니다

사용자가 버튼을 누르거나 화면을 마주했을 때, 지금 무슨 일이 일어났고 다음에 무엇을 할 수 있는지 화면 스스로 드러내야 합니다.

- **근거 요청**
  - 원칙 1과 원칙 5에서 파생된 기준입니다.
  - 2026-11-20: "새 세션 버튼 작동안하는데?"라는 문제 제기처럼, 동작이 실행되었으나 화면에 아무런 변화가 없어 고장으로 오해받은 사례를 근거로 합니다.
- **지금 구현**
  - 하단 상태 막대의 토글 버튼은 패널의 열림과 닫힘 상태를 시각적으로 표시합니다.
  - 열린 파일이 없는 빈 중앙 화면에는 다음에 할 일과 실제 동작하는 단축키 목록을 안내합니다.
  - 열린 파일이 없을 때는 `코드 정리` 버튼을 비활성화합니다.
  - 아직 확인하지 않은 변경 단계 수를 탭 제목(`확인 전 N`)에 실시간으로 표시합니다.
- **판단 기준**
  - 모든 사용자 동작은 화면에 눈에 보이는 변화를 만들어야 합니다. 비활성화된 모든 컨트롤은 왜 비활성화되었는지 화면의 맥락으로 설명되어야 합니다.

## 새 기능을 넣기 전 점검

UI를 바꾸거나 새 기능을 추가하기 전에 아래 6가지 질문을 모두 통과해야 합니다.

1. 이 변경은 어떤 사용자 요청이나 디자인 원칙을 위한 것입니까?
2. 앱을 켰을 때 이 요소가 스스로 열립니까? (스스로 열리면 안 됩니다.)
3. 화면의 기존 자리가 이미 같은 역할을 하고 있지는 않습니까?
4. 단축키를 Sublime, VS Code, PyCharm, Cursor에서 빌려왔으며, 화면의 버튼에도 그 단축키를 함께 적었습니까? 목록과 트리에서 더블클릭 같은 기본 마우스 동작이 작동합니까?
5. 기능을 실행했을 때 그 결과가 화면에 눈에 보이게 나타납니까?
6. `--ui-check`에 회귀 테스트(regression check) 항목을 추가했습니까?

## 이 원칙으로 고친 것 (2026-11-25)

위 원칙들을 적용하여 화면을 정리하고, 실제 윈도우 캡처 및 `--ui-check` 회귀 테스트(45/45 통과)로 검증을 마쳤습니다. 상세 요구사항은 `docs/srs.md`의 `FR-IDE-13`에 기록되어 있습니다.

- **빈 화면 안내 및 단축키 검증**: 열린 파일이 없을 때 중앙 영역에 "왼쪽 목록에서 파일을 고르세요" 문구와 단축키 목록(`⌘K ⌘B`, `⌘F`, `⇧⌘F`, `` ⌃` ``, `⌥⌘B`, `⌥⌘L`)을 표시합니다. 회귀 테스트 `empty_area_shows_next_step_and_shortcuts`는 화면에 적힌 모든 단축키가 실제 메뉴에 존재하는지도 함께 검사합니다.
- **Claude 패널 초기 닫힘**: 사용자가 `⌥⌘B`로 한 번 열기 전까지 Claude 패널은 닫힌 상태로 시작합니다 (`claude_panel_starts_closed`).
- **패널 열림 상태 표시**: 하단 상태 막대의 `터미널` 및 `Claude` 버튼이 각 패널의 열림 상태를 반영하여 보여 줍니다 (`panel_buttons_show_open_state`).
- **맥락에 맞는 버튼 비활성화**: 파일이 열려 있지 않을 때는 `코드 정리` 버튼을 비활성화합니다 (빈 화면 회귀 테스트에 포함).
